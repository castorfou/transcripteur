# Capture du micro et du Son système sous Linux et Windows

Note de recherche pour l'issue [#4](https://github.com/castorfou/transcripteur/issues/4). Question : comment capter en temps réel les deux **Sources** du MVP, le **micro** et le **Son système** (tout ce que la machine joue vers ses haut-parleurs, quelle que soit l'application), sous Linux puis sous Windows, en Python et en Rust, et livrer au **Moteur** un flux 16 kHz mono ?

Sources consultées le 2026-10-29. Quand une affirmation s'appuie sur du code, le lien pointe vers le fichier ou un commit figé. Les versions citées sont celles publiées à cette date : cpal 0.18.2, rubato 5.0.1, pipewire (crate) 0.10.1, libpulse-binding 2.30.1, wasapi (crate) 0.26.0, sounddevice 0.5.6, SoundCard 0.4.6, PyAudioWPatch 0.2.12.9, pulsectl 24.12.0, soxr 1.1.0 (registres [crates.io](https://crates.io/) et [PyPI](https://pypi.org/)).

## Résumé

- **Linux** : le Son système se capte comme une source ordinaire, le *monitor* de la sortie (sink) par défaut. Avec PulseAudio ou pipewire-pulse, c'est la source `<sink>.monitor`, ou le nom spécial `@DEFAULT_MONITOR@`. Avec l'API PipeWire native, c'est un flux de capture qui porte la propriété `stream.capture.sink=true`. Aucun droit particulier n'est nécessaire : l'utilisateur de la session a accès au socket du serveur son.
- **Windows** : le Son système se capte en **WASAPI loopback**. On ouvre un flux de capture sur le périphérique de *rendu*, en mode partagé, avec `AUDCLNT_STREAMFLAGS_LOOPBACK`. Depuis Windows 10 build 20348, on peut aussi capter une seule application (*process loopback*).
- **Rust** : **cpal** couvre les quatre combinaisons depuis la 0.18 (hôtes natifs PipeWire et PulseAudio, loopback WASAPI implicite). Il ne rééchantillonne pas en capture : on ajoute **rubato**.
- **Python** : aucune bibliothèque unique n'est fiable partout. **SoundCard** couvre Linux (libpulse) et Windows (WASAPI loopback) avec la même API, mais signale des bugs WASAPI connus. Sur Windows, **PyAudioWPatch** est l'option la plus éprouvée pour le loopback. **sounddevice** n'expose pas le loopback sur Windows, car ses wheels embarquent PortAudio 19.7.0. Pour le rééchantillonnage : **soxr**.
- **Commun aux deux OS** : le flux arrive au format du moteur de mixage (en général 48 kHz stéréo float32). Il faut donc le mixer en mono, le rééchantillonner à 16 kHz et gérer le changement de périphérique par défaut pendant une Session.

## 1. Vocabulaire système et correspondance avec le domaine

| Domaine (CONTEXT.md) | Linux (PulseAudio / PipeWire) | Windows (WASAPI) |
| --- | --- | --- |
| Source « micro » | *source* (`Audio/Source`), par défaut `@DEFAULT_SOURCE@` | endpoint de capture (`eCapture`) |
| Source « Son système » | *monitor* du sink par défaut (`@DEFAULT_MONITOR@`, `stream.capture.sink`) | flux loopback sur l'endpoint de rendu (`eRender` + `AUDCLNT_STREAMFLAGS_LOOPBACK`) |

Le terme « loopback » est réservé au vocabulaire Windows (CONTEXT.md demande de ne pas l'utiliser pour désigner la Source).

## 2. Linux

### 2.1 Mécanismes

**Les deux serveurs de son.** Ubuntu 24.04 livre PipeWire 1.0.5, Ubuntu 26.04 livre PipeWire 1.6.x ([Launchpad, paquet pipewire](https://launchpad.net/ubuntu/+source/pipewire)). Les applications PulseAudio y fonctionnent grâce à `pipewire-pulse`, qui réimplémente le protocole PulseAudio (module [`module-protocol-pulse`](https://gitlab.freedesktop.org/pipewire/pipewire/-/tree/master/src/modules/module-protocol-pulse)).

**Monitor côté PulseAudio.** Chaque sink expose une source `<nom_du_sink>.monitor`. On le voit dans l'exemple de `pulsectl` : `name='alsa-speakers.monitor'`, `desc='Monitor of Built-in Audio'` ([README pulsectl](https://github.com/mk-fg/python-pulse-control/blob/master/README.rst)). Les clients acceptent les noms spéciaux `@DEFAULT_SINK@`, `@DEFAULT_SOURCE@` et `@DEFAULT_MONITOR@` ([pacat(1)](https://gitlab.freedesktop.org/pulseaudio/pulseaudio/-/blob/master/man/pacat.1.xml.in)). Exemple de capture du Son système directement en 16 kHz mono :

```bash
parec --device=@DEFAULT_MONITOR@ --rate=16000 --channels=1 --format=s16le --latency-msec=50
```

**Monitor côté PipeWire natif.** La clé `stream.capture.sink` signifie « *Try to capture the sink output instead of source output* » ([keys.h](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/pipewire/keys.h)). Quand un client PulseAudio demande une source dont le nom finit par `.monitor`, `pipewire-pulse` retire ce suffixe pour cibler le sink et pose `stream.capture.sink=true` ([pulse-server.c](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/modules/module-protocol-pulse/pulse-server.c), fonction de création du flux d'enregistrement). Il gère aussi `@DEFAULT_MONITOR@` (même fichier, et [defs.h](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/modules/module-protocol-pulse/defs.h)). En ligne de commande : `pw-record --target <sink> -P '{ stream.capture.sink = true }'`. La cible accepte un `node.name` ou un `object.serial`, et l'option `-C/--monitor` enregistre depuis les ports monitor ([pw-cat(1)](https://docs.pipewire.org/page_man_pw-cat_1.html)).

**Format et rééchantillonnage serveur.** Par défaut, PipeWire tourne à `default.clock.rate = 48000` avec un quantum de 1024 échantillons, soit environ 21 ms ([pipewire.conf(5)](https://docs.pipewire.org/page_man_pipewire_conf_5.html)). Un flux qui demande un autre débit, par exemple 16 kHz mono, est converti par PipeWire. `pw-cat` expose `--rate`, `--channels` et `-q/--quality` (qualité du rééchantillonneur) ([pw-cat(1)](https://docs.pipewire.org/page_man_pw-cat_1.html)). Le README de cpal signale que ce rééchantillonnage peut provoquer des craquements à travers les couches de compatibilité ALSA, JACK et PulseAudio de PipeWire, et que l'hôte PipeWire natif y est moins sensible ([cpal README, « PipeWire Audio Glitches »](https://github.com/RustAudio/cpal/blob/master/README.md#pipewire-audio-glitches)). En pratique, pour la transcription : on capture au débit natif (48 kHz) et on rééchantillonne dans l'application (section 4), ou on laisse le serveur convertir avec une latence confortable (au moins 50 ms).

**Latence.** `pw-cat` utilise une latence de 100 ms par défaut ([pw-cat(1)](https://docs.pipewire.org/page_man_pw-cat_1.html)). La clé `node.latency` (par exemple `128/48000`) permet de demander une autre valeur ([keys.h](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/pipewire/keys.h)). Pour un Moteur qui traite des fenêtres de plusieurs centaines de millisecondes, viser 20 à 100 ms suffit. Une latence basse n'apporte rien et augmente le risque de xruns.

### 2.3 Rust sous Linux

- **cpal ≥ 0.18** ajoute des hôtes natifs PipeWire et PulseAudio (*features* `pipewire` et `pulseaudio`). L'ordre de préférence par défaut est PipeWire > PulseAudio > ALSA ([CHANGELOG 0.18.0](https://github.com/RustAudio/cpal/blob/master/CHANGELOG.md)). La compilation demande `libpipewire-0.3-dev` ou `libpulse-dev`, et ALSA reste nécessaire dans tous les cas ([README](https://github.com/RustAudio/cpal/blob/master/README.md)).
  - *Hôte PipeWire* : les nœuds `Audio/Sink` sont exposés comme périphériques *duplex*. Ouvrir un flux d'entrée dessus pose `STREAM_CAPTURE_SINK`, ce qui capte ce que joue le sink ([device.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/pipewire/device.rs#L166-L168), [commentaire](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/pipewire/device.rs#L994-L998)). Un pseudo-périphérique `default_sink` suit la métadonnée « sink par défaut » de WirePlumber, alors qu'un périphérique désigné précisément ne suit rien ([device.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/pipewire/device.rs#L141-L148)). Depuis la 0.18.2, un flux lié à un périphérique précis ne se réachemine plus automatiquement si ce périphérique disparaît ([CHANGELOG](https://github.com/RustAudio/cpal/blob/master/CHANGELOG.md)).
  - *Hôte PulseAudio* (crate pur Rust [`pulseaudio`](https://crates.io/crates/pulseaudio)) : l'énumération renvoie sinks et sources, et les sources comprennent les `.monitor` ([pulseaudio.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/pulseaudio.rs#L166-L183)).
  - *Hôte ALSA* : quand un serveur son tourne, il garde le périphérique ALSA `default` ; il faut alors passer par `pipewire` ou `pulse`, ou mieux par les hôtes natifs ([README](https://github.com/RustAudio/cpal/blob/master/README.md#alsa-pipewire-and-pulseaudio)).
- **libpulse-binding / libpulse-simple-binding** : liaisons de la libpulse C. Avec l'API *simple*, il suffit d'ouvrir un flux d'enregistrement sur `"<sink>.monitor"` ou `@DEFAULT_MONITOR@` au format voulu. Le serveur convertit, comme pour `parec`.
- **pipewire-rs** (crate `pipewire`) : API native complète. On crée un `pw_stream` avec `media.category=Capture`, `stream.capture.sink=true` et éventuellement `target.object`. C'est exactement ce que fait cpal ([device.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/pipewire/device.rs#L150-L172)), qu'on peut donc utiliser directement plutôt que de réécrire cette couche.

### 2.4 Pièges Linux

- **Droits** : aucun droit root ni groupe `audio` n'est nécessaire. Le client parle au serveur son de la session par un socket situé dans `$XDG_RUNTIME_DIR` (`pipewire-0`, [core.h](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/pipewire/core.h) ; `pulse/native`, [module-protocol-pulse.c](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/modules/module-protocol-pulse.c)). Ce répertoire appartient à l'utilisateur, en mode 0700 ([XDG Base Directory](https://specifications.freedesktop.org/basedir-spec/latest/)).
- **Changement de sortie par défaut pendant une Session** (casque branché, bascule HDMI) : si le flux vise `@DEFAULT_MONITOR@` ou le sink par défaut sans cible figée, WirePlumber le déplace. Le réglage `linking.follow-default-target` (vrai par défaut) déplace les flux applicatifs vers la nouvelle cible par défaut, et `node.restore-default-targets` mémorise les choix manuels ([WirePlumber, settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html)). La propriété `node.dont-reconnect` fait l'inverse : le nœud est détruit si sa cible disparaît ([keys.h](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/pipewire/keys.h)). Avec un nom figé (`alsa_output…analog-stereo.monitor`), le flux ne suit pas : il faut surveiller les événements (pulsectl, métadonnée `default.audio.sink`) et rouvrir.
- **Bluetooth** : quand une application ouvre le micro d'un casque Bluetooth, WirePlumber bascule le casque d'A2DP vers HSP/HFP, de moindre qualité, tant qu'un flux de capture existe (`bluetooth.autoswitch-to-headset-profile`, vrai par défaut) ([WirePlumber, settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html)). Conséquence : si la Source micro est le casque, le Son système capté sur ce même casque passe aussi en bande étroite. La documentation ne précise pas si un flux de capture du monitor (Son système seul) compte comme « *capture stream* » pour cette règle : **à tester** avec un casque Bluetooth, et sinon désactiver le réglage ou choisir un autre micro.
- **Sandbox** : sous Flatpak, `--socket=pulseaudio` donne accès au micro et à la lecture (« *sound input (mic), sound output/playback* ») et la documentation qualifie cette permission de sensible ([Flatpak, sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)). Côté PipeWire, un client Flatpak peut être restreint par objet ; c'est le session manager qui accorde les permissions ([PipeWire, Access control](https://docs.pipewire.org/page_access.html)). Pour un MVP distribué en paquet natif ou en binaire, la question ne se pose pas.

## 3. Windows

### 3.1 Mécanismes WASAPI

- **Loopback** : on obtient l'`IMMDevice` de l'endpoint de **rendu** (`GetDefaultAudioEndpoint(eRender, …)`), puis on initialise un flux de capture avec `AUDCLNT_STREAMFLAGS_LOOPBACK` ([Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)). Contraintes documentées :
  - **mode partagé uniquement** : « *Exclusive-mode streams cannot operate in loopback mode* » ;
  - le mode événementiel (`EVENTCALLBACK`) fonctionne en loopback seulement à partir de **Windows 10 1703** ;
  - les pilotes de confiance refusent de laisser capturer du contenu protégé par **DRM** ;
  - le loopback contient le mix de toutes les sessions Terminal Services ; sous Bureau à distance, l'audio redirigé passe par des périphériques propres à la session ;
  - le loopback WASAPI fonctionne même sans périphérique matériel « Stereo Mix ».
- **Conversion de format** : `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM` insère un matriceur de canaux et un convertisseur de fréquence entre le format demandé et le format de mixage. `SRC_DEFAULT_QUALITY` choisit un convertisseur de meilleure qualité ([AUDCLNT_STREAMFLAGS](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audclnt-streamflags-xxx-constants)). En théorie, on peut donc demander 16 kHz mono directement au moteur audio. cpal n'utilise cette conversion qu'en sortie (voir 3.3).
- **Silence** : quand rien n'est joué, le loopback peut ne fournir **aucun paquet** au lieu de paquets silencieux. SoundCard le contourne en mesurant le temps d'inactivité et en générant des zéros ([mediafoundation.py](https://github.com/bastibe/SoundCard/blob/a5cc715683df9f69759adc35bf585f9f2cd07b0a/soundcard/mediafoundation.py#L736-L756)), et traite le drapeau `AUDCLNT_BUFFERFLAGS_SILENT` ([AUDCLNT_BUFFERFLAGS](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/ne-audioclient-_audclnt_bufferflags)). Pour la transcription, ce trou n'est pas un problème tant que l'horodatage repose sur l'horloge murale et non sur le nombre d'échantillons reçus.
- **Process loopback** (option) : `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` via `ActivateAudioInterfaceAsync` inclut ou exclut l'audio d'un processus et de ses enfants. Disponible à partir de **Windows 10 build 20348** ([AUDIOCLIENT_ACTIVATION_TYPE](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-audioclient_activation_type), [exemple Microsoft](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)). Deux usages possibles : ne capter qu'une visio, ou exclure les sons de l'outil lui-même.
- **Changement de périphérique par défaut** : un flux WASAPI reste attaché à son endpoint. Pour suivre le défaut, il faut écouter `IMMNotificationClient::OnDefaultDeviceChanged`, appelé une fois par rôle (`eConsole`, `eMultimedia`, `eCommunications`), puis rouvrir le flux ([OnDefaultDeviceChanged](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immnotificationclient-ondefaultdevicechanged)).

### 3.3 Rust sous Windows

- **cpal** (hôte WASAPI par défaut) : utiliser un périphérique de **sortie** comme entrée active le loopback de façon transparente. La doc l'indique ([wasapi.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/wasapi.rs#L28-L31)) et le code ajoute `AUDCLNT_STREAMFLAGS_LOOPBACK` quand le flux de données est `eRender` ([device.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/wasapi/device.rs#L864-L868)). Concrètement : `host.default_output_device()?.build_input_stream(...)`.
  - Rééchantillonnage : `AUTOCONVERTPCM` n'est utilisé que pour les flux de **sortie**. En capture, « *only native formats will work* » ([device.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/wasapi/device.rs#L666-L668)). Il faut donc rééchantillonner dans l'application (rubato).
  - Défaut qui change : depuis la 0.18.0, les flux ouverts sur le périphérique par défaut se réacheminent automatiquement ([CHANGELOG 0.18.0](https://github.com/RustAudio/cpal/blob/master/CHANGELOG.md)) grâce à un `DefaultDeviceMonitor` ([device.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/wasapi/device.rs#L551-L562)). Le signalement de l'événement `DeviceChanged` a changé entre la 0.18.2 et la branche principale (correctif puis retour arrière, section *Unreleased* du CHANGELOG). Il vaut mieux tester ce comportement que s'y fier aveuglément.
  - Windows 10 minimum ([CHANGELOG, Unreleased](https://github.com/RustAudio/cpal/blob/master/CHANGELOG.md)).
- **wasapi** (crate) : liaison WASAPI de plus bas niveau. Elle gère la capture loopback et fournit un exemple `record_application` qui enregistre une seule application ([docs.rs/wasapi](https://docs.rs/wasapi/latest/wasapi/)). À retenir si l'on veut le *process loopback*, que cpal n'expose pas.

### 3.4 Pièges Windows

- **Bluetooth** : A2DP ne transporte que la sortie. Dès qu'une application ouvre le micro d'un casque, Windows bascule en HFP, mono en 8 ou 16 kHz. Sous Windows 11, les endpoints sont unifiés et la bascule est automatique. Sous Windows 10, il existe des endpoints « Stereo » et « Hands-Free » séparés, et l'audio envoyé vers « Stereo » est jeté pendant le mode HFP ([Bluetooth Classic Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/bluetooth-classic-audio)). Même effet que sous Linux : micro du casque et Son système haute qualité sur le même casque sont incompatibles.
- **Confidentialité du micro** : le loopback ne lit pas un micro. Le réglage « Autoriser les applications de bureau à accéder au micro » concerne la capture micro, pas le loopback, mais ce point n'a pas été vérifié dans la documentation Microsoft. **À tester.**
- **Mode exclusif** : le loopback n'existe qu'en mode partagé ([Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)). On en déduit, sans l'avoir vérifié, qu'une application qui tient l'endpoint en mode exclusif (certains lecteurs audiophiles) échappe à la capture, puisque son flux ne passe pas par le moteur de mixage.
- **DRM** : certains contenus protégés (lecteurs vidéo, navigateurs avec EME) peuvent être absents du loopback ([Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)).

## 4. Chaîne commune : vers 16 kHz mono

Quelle que soit la plateforme, le flux brut du Son système arrive au format du moteur de mixage : 48 kHz stéréo float32 par défaut sous PipeWire ([pipewire.conf(5)](https://docs.pipewire.org/page_man_pipewire_conf_5.html)). Sous Windows, c'est le *mix format* de l'endpoint, que cpal impose en capture ([device.rs](https://github.com/RustAudio/cpal/blob/4bedd4e98e9e58693a9d23505b2a4de9b726c321/src/host/wasapi/device.rs#L666-L668)). La chaîne commune :

1. **Callback audio** : copier les échantillons dans un tampon circulaire sans bloquer (ni allocation ni verrou dans le callback).
2. **Mixage en mono** : moyenne des canaux. SoundCard sous Windows impose de capter en stéréo (*known issue* ci-dessus).
3. **Rééchantillonnage 48 kHz → 16 kHz** :
   - *Python* : `soxr.ResampleStream(48000, 16000, 1, dtype='float32')`, conçu « *for real-time processing* » ([python-soxr README](https://github.com/dofuuz/python-soxr)).
   - *Rust* : `rubato`. Le rééchantillonneur synchrone `Fft` convient à un ratio fixe. La méthode `process_into_buffer()` « *performs no allocations or other operations that may block the thread* » ; pour 48 kHz → 16 kHz, ratio entier 3:1, le mode `FixedSync::Both` est possible ([docs.rs/rubato](https://docs.rs/rubato/latest/rubato/)).
   - Alternative sous Linux : demander directement 16 kHz mono au serveur (`parec --rate=16000 --channels=1`, ou un flux PipeWire à 16 kHz). Cela supprime cette étape côté application, mais rend le comportement dépendant de la plateforme.
4. **Découpage** en trames pour le Moteur (par exemple 20 à 30 ms pour une détection d'activité vocale, ou des fenêtres de plusieurs secondes).

Ce qui diffère selon l'OS et doit rester derrière l'interface de la Source :

| Aspect | Linux | Windows |
| --- | --- | --- |
| Désigner le Son système | `@DEFAULT_MONITOR@` / sink + `stream.capture.sink` | endpoint de rendu par défaut + loopback |
| Silence | flux continu (paquets) | possiblement aucun paquet |
| Suivre le défaut | session manager (WirePlumber), ou réouverture | `IMMNotificationClient` + réouverture (automatique dans cpal) |
| Conversion côté système | possible (serveur son) | possible avec `AUTOCONVERTPCM`, non exposée par cpal en capture |

## 5. Annexe : capter l'audio de l'hôte depuis un conteneur Docker

Utile pour le dev container, pas pour le produit. Le conteneur n'a pas de serveur son : il doit parler à celui de l'hôte par son socket.

- **Via le protocole PulseAudio (pipewire-pulse)** : monter `$XDG_RUNTIME_DIR/pulse/native` de l'hôte et définir `PULSE_SERVER=unix:/chemin/monté/native`. `PULSE_SERVER` désigne le serveur auquel se connecte un client libpulse ([pulseaudio(1)](https://gitlab.freedesktop.org/pulseaudio/pulseaudio/-/blob/master/man/pulseaudio.1.xml.in)). pipewire-pulse vérifie seulement la **longueur** du cookie d'authentification, pas sa valeur ([pulse-server.c, `do_command_auth`](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/modules/module-protocol-pulse/pulse-server.c)). Un vrai PulseAudio, lui, exige le cookie de l'hôte.
- **Via PipeWire natif** : monter le socket `pipewire-0` et définir `PIPEWIRE_RUNTIME_DIR` (ou `XDG_RUNTIME_DIR`) et, si besoin, `PIPEWIRE_REMOTE` ([pipewire(1)](https://docs.pipewire.org/page_man_pipewire_1.html), [core.h](https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/master/src/pipewire/core.h)). cpal détecte aussi un socket situé dans `/run/pipewire` quand ces variables sont absentes ([CHANGELOG, Unreleased](https://github.com/RustAudio/cpal/blob/master/CHANGELOG.md)).
- **Contraintes** : le répertoire `$XDG_RUNTIME_DIR` de l'hôte est en mode 0700 et appartient à l'utilisateur ([XDG Base Directory](https://specifications.freedesktop.org/basedir-spec/latest/)). Il faut donc lancer le conteneur avec le même UID, ou monter le socket lui-même. Les sources monitor sont alors visibles comme sur l'hôte. Sous Docker Desktop (VM) ou WSL, le socket de l'hôte n'est pas accessible directement : non étudié ici.

## Ce que ça implique pour la décision

**Synthèse.** Capter le Son système est un problème résolu sur les deux OS, mais par deux mécanismes différents : le monitor du sink sous Linux, le loopback WASAPI sous Windows. Le reste de la chaîne est commun et indépendant de l'OS : mixage mono, rééchantillonnage 16 kHz, découpage, horodatage. La Source doit donc être une interface étroite (« donne-moi des trames 16 kHz mono float32 ») avec une implémentation par OS derrière. Trois comportements varient selon l'OS et doivent être absorbés par cette interface : les trous de silence, le changement de sortie par défaut pendant une Session et la bascule Bluetooth. Aucun ne demande de droits particuliers dans le cas d'une application native.

**Recommandation Rust.** Prendre **cpal ≥ 0.18**, avec la feature `pipewire` (et `pulseaudio` en repli), plus **rubato** pour le passage à 16 kHz. Une seule API couvre micro et Son système sur Linux (`default_sink` ou un sink en entrée) comme sur Windows (sortie par défaut en entrée), et cpal gère déjà le suivi du défaut. On ne descend au crate `wasapi` que si l'on veut le *process loopback*. Point d'attention : l'hôte PipeWire de cpal est récent (0.18.0, juin 2026) et son CHANGELOG contient encore de nombreux correctifs. Prévoir un prototype sur Ubuntu 24.04 et 26.04.

**Recommandation Python.** Pas de bibliothèque unique satisfaisante. Le plus simple à court terme : **SoundCard** sur les deux OS (même API, monitors et loopback via `include_loopback=True`), toujours en stéréo puis mixage mono, et **soxr** pour le rééchantillonnage. En cas de souci WASAPI (*known issues* de SoundCard), basculer sur **PyAudioWPatch** pour Windows. Garder `parec` / `pw-record` en sous-processus comme repli Linux. Éviter sounddevice pour le Son système tant que ses wheels Windows embarquent PortAudio 19.7.0. Si le choix du langage est encore ouvert, Rust offre ici une base plus homogène (une bibliothèque, un modèle d'erreurs, suivi du défaut intégré). Python demande d'assembler deux ou trois bibliothèques selon l'OS.
